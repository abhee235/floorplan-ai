# ADR-001: Scene IR is the single source of truth; units, coordinates, and entity model

Status: Proposed
Date: 2026-09-14
Supersedes: section 5.1 of 00-brainstorm.md
Ledger lines this ADR must satisfy: W-001..W-012, W-013..W-017, W-029, W-030, W-041, W-048, W-092..W-096, O-001..O-016, O-038..O-050, R-001..R-020, R-101..R-124, F-001..F-021, F-062, F-070, P-024, P-027..P-036, P-050, P-052, P-060

## Context

The previous attempt went from pixels to three.js geometry with no model in
between, so nothing could be corrected, furnished, or costed. A small 2D
semantic model with 3D derived from it is what makes a plan correctable. We
need that model as plain JSON with ids rather than object references, with one unit system, and with the
extra concepts an office planner needs: room purpose and capacity, mount
points, parent links for stacked items, and provenance from plan reading.

The model must also be friendly to mid-sized language models that will call
tools against it: whole numbers, short readable ids, explicit enumerations,
no derived values that could disagree with stored ones.

## Decision

### D1. The Scene IR is the only state

Every subsystem reads the IR or derives from it. Nothing else holds state that
is not recoverable from the IR plus the catalog: not the three.js scene, not
the plan canvas, not the agent. The IR is a plain JSON document validated by a
zod schema in the `ir` package, which also generates the TypeScript types and
the JSON Schema used by tool definitions.

### D2. Units and angles

- Lengths are **integer millimetres**. No floats for lengths anywhere in the
  IR. Sub-millimetre precision has no meaning in this domain, integers avoid
  drift in polygon booleans, and spec sheets are in millimetres.
- Angles are **degrees**, stored as numbers, normalised to the half-open range
  from 0 to 360 on write (ledger F-001, R-020).
- Fractions (embed fractions on openings, drop-on-top ratios) are numbers from
  0 to 1 and are validated to that range on write; a value outside it is
  refused, not accepted (O-005).
- Currency amounts live in the catalog, not the IR.

### D3. Coordinate system

- Plan coordinates: x to the right, **y up**, origin at the project origin,
  as in CAD and DXF, not y down as in screen space, because every importer
  and exporter we care about is y up.
- Rotation about the vertical axis is **counter-clockwise positive** when
  viewed from above, 0 degrees pointing along +x.
- Elevation is measured from the level's floor, in millimetres, and may be
  negative (F-012).
- 3D mapping is fixed by the engine, not the IR: plan (x, y) maps to three.js
  (x, elevation, -y), which keeps a right-handed frame with y up.

### D4. Identifiers

- Every entity has a string id of the form `<type>_<6 base36 chars>`, for
  example `wall_k3x9q2`, `room_7hp01a`. The type prefix lets a model and a
  human tell entities apart; the short random suffix stays readable in tool
  calls. Ids are unique within a project and never reused after deletion.
- Cross references are always ids, never embedded objects and never indices.
- Ids are generated by an injectable generator so tests are deterministic.

### D5. Entity model

Written here as TypeScript-flavoured notation; the zod schema is the
normative form and lives in `packages/ir`.

```
Project {
  schemaVersion: number            // integer, migrations are forward-only
  meta: { name, createdAt, updatedAt, currency, north?: degrees }
  levels: Level[]                  // at least one, always
  walls: Wall[]
  openings: Opening[]
  rooms: Room[]
  items: Item[]
  zones: Zone[]
  annotations: Annotation[]
  catalogRefs: Record<productId, ProductSnapshot>
  provenance?: Provenance
  properties?: Record<string, string>   // forward-compatible bag
}

Level { id, name, elevation: mm, height: mm, floorThickness: mm, index: number }
  // ordered by (elevation, index); index breaks ties for levels at one elevation (R-105, R-106)

Wall {
  id, levelId
  start: Point, end: Point         // mm; start != end (W-004 rejected)
  thickness: mm                    // > 0 (W-006, W-007 rejected)
  height?: mm                      // default: level.height (W-092)
  heightAtEnd?: mm                 // sloped top when present and different (W-093, W-094)
  arcExtent?: degrees              // absent or 0 means straight (W-048); |value| <= 270 (W-060)
  kind: "exterior" | "interior" | "partition" | "glass"
  joins: { start: Join | null, end: Join | null }
  finishes?: { left?: FinishRef, right?: FinishRef, top?: FinishRef }
}
Join { wallId, end: "start" | "end" }
  // invariant: reciprocal; a wall may not join itself (W-015 rejected, W-030 fixed);
  // joined endpoints share identical coordinates (W-068, W-069)

Opening {
  id, levelId, wallId
  kind: "door" | "window" | "passage"
  position: fraction               // centre along the wall centreline, 0 at start
  width: mm, height: mm, sill: mm  // sill measured from level floor
  swing?: { hinge: "start" | "end", direction: "left" | "right" }   // relative to wall direction; tools expose compass words
  mirrored: boolean
  productId?: string               // for BOM; embed fractions and cut-out shape come from the product or recipe
  recipe?: OpeningRecipe           // parametric fallback when no product
}
  // An opening belongs to exactly one wall. Moving a wall moves its openings.
  // Deleting a wall deletes its openings (O-050 replaced by explicit behaviour).
  // Overlapping openings on one wall are rejected by validation (O-060 not needed).

Room {
  id, levelId, name?
  polygon: Point[]                 // >= 3 points, counter-clockwise, simple (R-150 rejected)
  holes?: Point[][]                // clockwise
  purpose: RoomPurpose             // meeting | huddle | boardroom | training | open-office | focus | reception | cafeteria | corridor | utility | other
  capacity?: number
  ceilingHeight?: mm               // override; default level.height
  finishes?: { floor?, ceiling? }
  source: "manual" | "detected" | "imported"
}

Item {
  id, levelId
  ref: { productId } | { recipe: PrimitiveRecipe }
  position: Point, rotation: degrees, elevation: mm
  size?: { w, d, h }               // override of product size, only when the product is deformable
  mirrored: boolean
  mount: { kind: "floor" | "wall" | "ceiling" | "table" | "item", targetId?: string, height?: mm }
  parentId?: string                // stacking parent (F-070 replaced: moving the parent moves the child)
  roomId?: string                  // validated against polygon containment, recomputed on move
  tags?: string[]
}

Zone { id, levelId, polygon, kind: "desk-cluster" | "circulation" | "av-coverage" | "other", rule?: ArrangementRule }
  // a desk cluster keeps its generating rule so it can be regenerated

Annotation { id, levelId, kind: "scale-bar" | "north" | "label" | "dimension" | "note", ... }

Provenance { sourceFile?, reader?: string, confidence?: number, questions: string[] }
```

### D6. Invariants enforced by validation, not by convention

The `ir` package exposes `validate(project)` returning a list of problems with
entity ids and codes. A project with problems can be loaded and shown but not
exported and not accepted as a tool result. Invariants include: at least one
level; every levelId, wallId, roomId, parentId resolves; joins reciprocal and
never self-referential; joined endpoints coincide; wall thickness positive
and start distinct from end; opening width fits within its wall length at its
position; openings on one wall do not overlap; room polygons simple with at
least three points; item elevation plus height within a sane bound; no cycles
in parentId.

### D7. Derived values are never stored

Wall length, room area, bounding boxes, plan footprints after rotation, and
ground elevation are computed by functions in `ir` and returned by tools, never
persisted (ledger F-009 shows the cost of storing them).

### D8. Schema versioning

`schemaVersion` is an integer. Loading an older version runs forward-only
migrations in order. Unknown fields are preserved through load and save so a
newer file survives an older tool (P-037). Selection, undo history, and view
state are never part of the IR (P-052).

## Alternatives considered

- **Metres as floats.** Rejected: drift in polygon booleans, and small models
  handle whole numbers better than decimals.
- **Centimetres.** Rejected: furniture and AV specs are in
  millimetres and we would carry decimals for door thicknesses.
- **Y down plan coordinates.** Rejected: every importer and
  exporter is y up; one flip at the viewer is cheaper than flips everywhere.
- **Openings as furniture bound spatially.** Rejected: a binding by
  position breaks as walls move (O-017..O-050, O-102..O-111). Agents and the BOM need to ask
  which wall a door is in without geometry.
- **UUIDs for ids.** Rejected for readability in tool calls; a 6-character
  base36 suffix gives over two billion values per type, ample for one project.

## Consequences

- Every ledger line about walls, openings, rooms, levels, and furniture now has
  a concrete field to test against.
- Importers must convert units and flip y once, at the boundary.
- The catalog carries the door and window intelligence (embed fractions,
  cut-out shape, mesh rotation), so ADR-008 must define those fields.
- Tools must never accept or return floats for lengths; ADR-006 inherits this.
- The engine owns the 3D mapping; ADR-003 inherits (x, elevation, -y).
